# OpenCode V2.3.2: local session storage

**Source verification only.** Upstream [`v2.3.2`][release] resolves to [`c0ad18b402eb2827fc1ee71c171b1177b3fc02d1`][commit]; the docs and implementation linked below are from that commit. No local OpenCode runtime or personal session database was inspected.

## SQLite and change detection

- **The local server owns one SQLite database, not a transcript file per session.** `opencode debug paths db` computes the effective path without starting the server or opening the database. `OPENCODE_DB` overrides it (absolute path, relative to the data directory, or `:memory:`). The built-in `latest`, `dev`, `beta`, `next`, and `prod` channels use `opencode.db`; other channels can use `opencode-<channel>.db`. Data lives under `${XDG_DATA_HOME:-$HOME/.local/share}/opencode`. Local SQLite enables WAL and foreign keys; reading a copy of only the main file while the service is running can miss committed changes in the WAL. [CLI docs][cli] · [Path resolver][path] · [XDG roots][roots] · [Server launch][launch] · [Database setup][db]
- **The V2 transcript is a mutable projection.** `session_v2` is the session record; `session_message` holds typed JSON rows ordered by `(session_id, seq)`, not by update time or ID. User payloads are on message rows. Assistant content is normally inline too; with `experimental.part_rows`, assistant content can be in `session_part`, ordered by `(message_id, ordinal)`. The read path handles both layouts. `session_inbox` is pending input, not admitted transcript; optional media storage uses `blob` and `blob_ref`. The message reader pages by sequence and reconstructs the message shape. [SQL schema][sql] · [Projector][projector] · [Message reads][store] · [History decoder][history]
- **`event_sequence.seq` is a per-aggregate watermark, not a stream of row changes.** Durable event publication advances it in the same transaction as projection; events can update existing messages, advance with no new message, or delete messages. Non-durable events need not advance it. The local CLI does not opt into payload retention: `Bus.configured` defaults `persist` to `false`, so neither `event` nor `GET /api/experimental/session/:sessionID/log` is a complete local replay source. The workerd server explicitly enables retention. `session_v2.time_updated` is recency, not a mutation counter: several projectors explicitly preserve it. A reader can use the watermark to find candidates for re-reading, but cannot fetch changes by asking for only message rows above the previous watermark; it must also reconcile deletions and account for migrations/imports. [Event tables][event-sql] · [Bus][bus] · [Local launch][launch] · [Server wiring][routes] · [Workerd][workerd] · [Projector][projector]

## File changes, revert, and compaction

- **File changes are inferred from Git snapshots, separate from SQLite.** The runner attempts start and terminal snapshots for each model step, including recorded failures. The assistant message stores `snapshot.start`, `snapshot.end`, and changed `snapshot.files` when available; the trees and file contents are under `<data>/snapshot/<project-id>/<hash-of-real-worktree>`, not in the transcript DB. Capture is best-effort, Git-only, and scoped to the active directory; it excludes ignored files and untracked files over 2 MiB. The turn diff route compares the first recorded start to the last end (or the live tree for a running step) and rejects ranges spanning a location change. This measures changes between captures, not who wrote each file; it cannot roll back external side effects such as processes or database effects in general. [Snapshot docs][snap-doc] · [Capture][snapshot] · [Runner][step] · [Message projection][updater] · [Turn diff][diff]
- **Staging a revert and committing it are different.** Stage writes a `session_v2.revert` boundary without deleting message rows, and by default restores affected paths to the snapshot before their first reverted assistant step. `files: false` allows conversation-only staging; clear/redo removes the boundary and restores the saved original state for affected paths. An explicit commit, a new prompt, or manual compaction can commit it: the projector then deletes message rows at or after the boundary (with cascading part deletes), removes corresponding pending inbox entries, rewinds instruction state, and releases media refs. Thus the snapshot docs' “not from durable session history” is **not** a guarantee that a local SQL reader can recover the reverted tail: it is removed from the projection, default local event payload retention is off, and snapshot objects are separate. [Snapshot docs][snap-doc] · [Revert implementation][revert] · [Session operations][session-ops] · [Projector][projector] · [Bus][bus]
- **Compaction changes model context, not transcript retention.** A completed compaction is a message/checkpoint in the projection. Local summaries can reference the first retained message via `metadata.keepID`; context reads reconstruct the retained tail without deleting older rows. Native compaction can store an opaque provider checkpoint; on an incompatible model the original conversation is available instead. Background summaries held ahead of use are in memory. Distinguish transcript reads from the model-context endpoint and from a separate revert that happens to be committed when compaction is requested. [Compaction docs][compact-doc] · [Compaction implementation][compact] · [History reads][history] · [API definitions][protocol]

## Forks, subagents, and imports

- **A fork copies; a subagent starts fresh.** Fork creates a new, top-level session (`parent_id = NULL`, `fork_session_id` plus `fork_boundary`), copying settled projected messages strictly before `before`, or through the latest message if omitted. Copied messages get new IDs and retain their original sequence values; the projector also copies split parts and remaps compaction `keepID`. This is a conversation fork at the same location, not a Git worktree or a filesystem rollback. New subagents instead have `parent_id` set, inherit the parent's location, receive a new task prompt without a copy of its transcript, and report back in the background. Passing an existing child ID continues that child. [Fork operation][session] · [Fork projector][projector] · [Agents docs][agents-doc] · [Subagent tool][subagent]
- **Session JSON transfer is not event replay or a storage backup.** `opencode session export` produces `{info, messages}` from the settled projection; import accepts a local JSON file or HTTP(S) URL and binds it to the chosen directory. It preserves the session and message IDs, assigns fresh message sequences from array order, conflicts on an existing session ID, and requires any referenced parent to exist first. It writes projected rows and reserves their sequence range; it does not recreate the original event log, fork lineage fields, or snapshot object database. The API normalizes some pre-2.1 V2 message fields before validation; that is not evidence for arbitrary V1 JSON compatibility. [CLI docs][commands] · [Import handler][import] · [Transfer implementation][transfer] · [API definitions][protocol] · [Upstream compatibility tests][import-test]
- **V1 database migration is a different path.** The Bun migration detects the old `session` table in the opened DB, converts legacy `session`/`message`/`part` rows into V2 projections, and can also read a compatible `opencode-next.db` read-only during that migration. It seeds session sequence watermarks without reconstructing old event payloads (the migration initially clears old `event` rows). Node and workerd select a no-op for this legacy migration. [Bun migration][v1] · [Runtime selection][core-package]
