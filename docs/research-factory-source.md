# Factory Droid as a read-only Spool source

**Recommendation:** Start with an opt-in, same-machine source that reads persisted Droid transcripts, not a Factory cloud connector. Factory documents local session storage and a hook-provided transcript path; it does not document the on-disk record format as a stable integration contract. Ship a conversation-only adapter only after testing a narrowly identified format against synthetic fixtures and proving it can reopen indexed matches against the original source. [Hooks][hooks] · [TypeScript SDK][ts-local] · [Session Contents Sync][sync] · [Spool reader contract][reader]

## What Factory documents

| Surface | Documented capability and fit |
| --- | --- |
| **Local saved sessions** | The TypeScript and Python SDKs expose `listSessions()` / `list_sessions()`, which enumerate local saved sessions without starting Droid (the TypeScript docs also explicitly say it does not call the Factory API). These methods provide catalog information; the reviewed SDK guides do not document a local, offline bulk history export. Resuming a session and streaming a turn is not passive history access. The CLI's `/sessions` and `--resume` are interactive navigation/resume, not export. [TypeScript SDK][ts-local] · [Python SDK][py-local] · [CLI reference][cli] |
| **Lifecycle hooks** | Hook input includes `session_id`, `transcript_path`, and `cwd`. The docs illustrate the path with a `.jsonl` file under `.factory/projects`; the example does not establish a universal root, naming scheme, or record schema. `SessionEnd` reports the number of message records but is not a completeness/flush contract and does not fire when merely viewing a remote session. `SessionStart` also runs on resume and after compaction. A hook could provide a local discovery hint in a later phase, but must not be required for history, coverage, or consistency. Do not register hooks for the MVP. [Hooks: input][hooks] · [Hooks: events][events] |
| **Public REST history** | The org-gated Droid Sessions API provides authenticated GETs for the user's session list, one session, child sessions, paginated message history, and an individual message. Message pages accept `cursor`, `limit` (1–100), optional `role`, and optional `computerId` to query a computer directly; the SDK documents newest-first paging. The public contract is for typed message objects, not the original persisted bytes, physical record order, or a frozen Spool-compatible snapshot across requests. Using GET alone would be read-only with respect to the upstream session, but it still requires bearer authentication, authorized network access and a separate source model. Retain the option as separate future work, not a fallback for local reads. [Sessions API][sessions] · [OpenAPI][openapi] · [API authentication][api] · [TypeScript SDK][ts] |
| **Export, sharing and streaming** | No dedicated bulk export of already-persisted Droid transcripts or stable disk schema was identified in the reviewed docs index, CLI reference, SDK guides, or public OpenAPI. That is a documentation finding, not a claim about every product UI or private API. `/share` publishes an organization-accessible link rather than exporting locally. `droid exec --output-format` serializes the result or live events of a run, not a passive historical dump. Optional telemetry message spans go to a configured collector and can truncate attributes; do not use them as transcript evidence. [Docs index][index] · [CLI reference][cli] · [OpenAPI][openapi] · [Droid Exec][exec] · [Telemetry privacy][otel] |

**Cloud sync is not required for local ingestion.** Factory's enterprise controls explicitly say that with Session Contents Sync (`cloudSessionSync`) off, contents stay on the computer that ran the session while Factory still stores session metadata. Web or desktop viewing from another computer then requires the original computer to be online. Here, *local* means available through the authorized filesystem of the machine running Spool, not every session visible in the Factory UI. The workstation MVP should not expect cloud-computer sessions or histories from other workstations to be mirrored locally. A separately authorized deployment on the machine that ran a session could be evaluated on its own merits. [Session Contents Sync][sync] · [Factory App overview][app]

**Remote access and cloud storage are distinct.** Cloud-stored message history cannot be assumed when sync is off. The documented `computerId` option is a separate live-computer route; the reviewed API docs do not establish which sync settings, computer types, roles, or disconnected states allow which reads. Do not assume REST has all local sessions, cannot see any sync-off sessions, or can serve byte-exact evidence. Before any remote design, verify that access matrix using an explicitly authorized test organization and synthetic sessions; treat unavailable or incomplete scans as such, never as evidence of deletion. [Session Contents Sync][sync] · [Sessions API][sessions] · [Spool spec, §§7.3, 14.2][spec]

## Observed local format

A read-only, structure-only scan on macOS with Factory App 1.20.0 inspected `~/.factory/sessions/<project>/<session-id>.jsonl`. It recorded field and record shapes and aggregate counts, not transcript content, session IDs or project paths. This is evidence for one machine and one installed build, not a format guarantee.

- All 571 JSONL files in that scan started with `type: session_start`, `version: 2`, and an `id` matching the file stem. Headers had `cwd` and `title`; one header also had `callingSessionId` and `callingToolUseId`. There were 571 `.settings.json` sidecars. The source can take its identity from the transcript header rather than decoding a directory name or reading the sidecar.
- Only 3 of the 571 files contained message records, including the running Factory desktop session that initiated this research. The scan found 223 messages total. This was the user's first substantive use of Factory, so the count is not a test of historical coverage, cloud sync, or deletion.
- A message record has `type: message`, `id`, `timestamp`, and a nested `message` with `role` and `content`. The observed messages used `user` and `assistant` roles and block arrays. In particular, `user` records held both ordinary `text` blocks and `tool_result` blocks in this corpus, so role alone is not a safe search filter. Assistant records included `text`, `tool_use`, and `thinking`. `todo_state` and `agent_turn_outcome` also appeared as non-message records.
- Non-root messages in the scan used `parentId`, which always resolved to a preceding record in that file. The observation does not establish fork or compaction semantics, how to select a branch tip, how to distinguish every injected user text block, or when Factory rewrites a transcript. Check these with controlled sessions before release.
- A later structure-only check identified `visibility: llm_only` on text-bearing user envelopes and `visibility: user_only` on a text-bearing notice marked `systemNotice`. Neither is an ordinary conversational message. Text-bearing assistant envelopes also carried `openaiPhase` values `commentary` and `final_answer`.

## Fit with Spool

- **Discovery and ingestion.** Spool already has an enabled-source registry, owner-checked local roots and paged `.jsonl` scanning. The JSONL route uses bounded discovery probes and a shared streaming parser with per-record digests and locators. If empirical evidence supports one file per session with safe record boundaries, add a Factory-specific identity probe and classifier to that path, not a new daemon, Python/Node runtime, or credentialed client. Narrow the configured allowlist to transcript roots rather than scanning all Factory state. An extension alone is not proof of a transcript. If identity or meaningful content depends on multiple mutable files or a database, first characterize coherent observation and safe re-resolution; do not force it through the JSONL route. OpenCode's separately routed SQLite source is precedent for a different storage model, not evidence Factory needs one. [Source registry][registry] · [Safe roots and scan][roots] · [Discovery probe][probe] · [Shared parser][jsonl] · [Read source routing][locator]
- **Observation and publication.** Reuse current debounce/watermark and incomplete-scan behavior, then stage bounded reads ending at a complete record boundary and use the existing guarded publication transaction. Metadata is a change signal, not identity proof. Reparse a changed source; don't assume append-only storage or infer write behavior from a documented UI operation such as fork, compaction, or archive. Verify selected records by digest on read and defer publication when a rewrite has been detected. Document supported variants, fail closed on unknown critical formats, and bind parser changes into the pipeline fingerprint. [Discovery][discover] · [Spool spec, §§7–9][spec] · [Publication][publish] · [Pipeline fingerprint][fingerprint] · [CLI reference][cli]
- **Search classification.** Retain only proven user/assistant conversational blocks, with the contract's narrow exception for structured user-input exchanges once that mapping is verified. Exclude raw tool I/O, reasoning, developer/system content, injected context, and generated summaries from the searchable corpus. Leave subagents out by default, keep separate sessions separate, and don't deduplicate by equal text or invent a branch path. Support straight-line history only if the observed format establishes it; skip or mark unsupported forms rather than flattening ambiguous ancestry. Unknown critical shape/identity must not look like a successfully indexed empty transcript. [Spool spec, §§5–6 and 8.3][spec] · [Spool reader contract, §§4–5][reader]
- **Verified reads are a release gate.** Search yields discovery excerpts, while a match reference pins canonical messages and expected digests. `read_session` must safely reopen the allowlisted source and verify original records, keep a finite branch selection across pages, and respect current source enablement and exclusions. `prefer_source` may use an explicitly labelled indexed copy only when verification is unavailable; a known mismatch is `SOURCE_CHANGED` or `STALE_REFERENCE`, never silent fallback. Verified excerpts require original-source verification. Normalized API objects are not byte-exact raw records; a future API source would need a separate identity, observation and provenance contract. `with_tools` requires proven turn ownership, not adjacency. Follow the existing OpenCode precedent of `VIEW_NOT_SUPPORTED` for unsupported views rather than approximating them. [Spool reader contract, §§3–6, 9–10][reader] · [Locator verification][locator] · [OpenCode view gate][viewgate]

## Phased MVP and acceptance tests

1. **Format gate.** Identify the supported Droid build(s), transcript layout, an unambiguous format probe, canonical IDs and record boundaries, and whether append, resume, fork, compaction, archive, move or replacement affect identity and read consistency. Separate public guarantees from observations. Determine how to recognize top-level sessions and genuine conversation vs synthetic messages before broad discovery. Use synthetic format fixtures, never copied personal transcript bytes, and avoid recording real session IDs, project paths, or contents. If safe identity and provenance cannot be established, stop at research and ask Factory for a supported local inspection/export API. [Hooks][hooks] · [CLI reference][cli] · [Spool spec, §§5–8][spec]
2. **Ship an experimental, conversation-only local source.** Explicit roots and opt-in; no automatic enablement, hooks, sync changes, writes to Factory state, runtime launch, or network calls by the adapter. Prove the lexical-only path with hosted processing disabled: discovery → ingestion → search → `read_session` with verified provenance, including a known unindexed source read without indexing or embedding it. No unsupported raw or tool views. Synthetic conformance cases: accepted and rejected probes, mixed roles/blocks and unknown types, structurally similar non-transcripts, subagent exclusion, duplicates and fork/compaction cases as applicable, invalid or incomplete lines, UTF-8 and large records, bounds and cancellation. Integration cases: roots/owner/symlink checks, paged discovery and watermark reconciliation after restart, incomplete/unavailable roots, append during scan/read (frozen old cursor), rewrite/truncation/replacement and safe rename, missing-source fallback vs mismatch, user exclusion after issuing a cursor, byte-budgeted pagination and unchanged source bytes. Use a temporary `SPOOL_HOME` and only synthetic roots, with an executable smoke test and targeted adapter/discovery/ingest/reader tests. [Adapter verification][adapter-tests] · [Spool reader acceptance tests][reader] · [Contribution verification][contributing]
3. **Expand only with evidence.** Add versioned fixtures before advertising more Droid variants, and add branches, tools, or raw reads only once native ancestry, ownership, or original-record byte fidelity can be demonstrated. If needed, an opt-in hook can only wake discovery for an already authorized local source; validate hints like all other locators, and do not serialize hook payloads. Keep remote access a separate design with policy, pagination, stable observation, rate limits and credentials addressed explicitly. Factory Session Contents Sync and Spool hosted processing are independent; spinning up a local source is not permission to send transcript text to a hosted embedder.
